# What Iris can take from Archify

## Findings

- **Give the swarm map an evidence drill-down.** The map already answers which Runs attempted to reach which destinations. A selected Run should answer what Iris saw, what Verify read, and why the Run stopped or needs a human check. Keep this on the existing Run page.
- **Borrow the handoff from picture to source.** Archify links a diagram element to the code behind it. Iris can link a call or verdict to the local journal entries and read-back details that support it. Show the recorded verdict at the top and keep the evidence close by.
- **Use a sequence for one Run.** Keep the swarm map as the overview. In the Run view, label the attempted destination, mark where Iris blocked a call, and put the Verify and Steer steps where they occurred. The same journal should produce the same view.

## How Archify works

**The host agent authors the content.** For an idea or plan, it reads the request, picks a diagram type, and writes a JSON candidate with the nodes, relationships, labels, and any needed conditions. For Mermaid input, the skill tells the agent to carry the meaning and connections into native JSON. For a codebase, the agent starts at the relevant entry point and follows the requested behavior through calls, branches, and effects. It records the repository and commit and adds source paths and line ranges to the candidate. The separate Code Analysis command is for repository health and coupling. It is outside the normal authored diagram path. [Skill](https://github.com/tt-a1i/archify/blob/main/archify/SKILL.md) · [Repository authoring](https://github.com/tt-a1i/archify/blob/main/archify/references/repository-authoring.md)

**The Node CLI compiles the candidate.** It dispatches by diagram type. The architecture renderer lays out the authored components, routes the relationships, and draws SVG. A shared writer puts that SVG, the cards, and source metadata into standalone Viewer HTML. The Viewer offers search and path exploration. For a repository-backed diagram, the evidence checker uses Git objects at the pinned commit to check paths and line ranges. The author still has to read the lines and establish that they support the claim. [CLI](https://github.com/tt-a1i/archify/blob/main/archify/bin/archify.mjs) · [Architecture renderer](https://github.com/tt-a1i/archify/blob/main/archify/renderers/architecture/render-architecture.mjs) · [HTML writer](https://github.com/tt-a1i/archify/blob/main/archify/renderers/shared/cli.mjs) · [Evidence checker](https://github.com/tt-a1i/archify/blob/main/archify/renderers/shared/repository-evidence.mjs) · [Viewer guide](https://github.com/tt-a1i/archify/blob/main/archify/references/viewer-runtime.md)

**An explainer starts with a structured Markdown draft.** The agent writes the conclusion, its reasons, and one panel per reader question. Directives describe steps, tables, charts, diagrams, and sources. The preparation code parses and validates the draft, resolves sources, and prepares native diagrams from inline specs or local files. The page renderer embeds diagram previews and links to full interactive views. Steps can highlight the part of the diagram they explain. [README](https://github.com/tt-a1i/archify#ask-a-question-get-a-one-page-answer) · [Draft format](https://github.com/tt-a1i/archify/blob/main/archify/references/explainer-authoring.md) · [Preparation](https://github.com/tt-a1i/archify/blob/main/archify/explainer/prepare.mjs) · [Embedded diagrams](https://github.com/tt-a1i/archify/blob/main/archify/explainer/diagrams.mjs) · [Page renderer](https://github.com/tt-a1i/archify/blob/main/archify/explainer/render.mjs)

**`finalize` checks the artifact in stages.** It validates the candidate and delivers HTML, then checks the delivered artifact against its provenance. Native diagrams also get an automated Chrome check. For explainers, that browser step requires `--browser-check`. The receipts tie the checks to the candidate and output bytes. The browser check measures properties such as fit. A reader still needs to follow the arrows and check the meaning against the source. ## What it chooses to show

The question sets the scope. An architecture view follows the main user journey. A sequence shows exchanges and returns. A lifecycle shows state changes. A waterfall shows duration and overlap. The agent groups cooperating roles when that keeps the path clear. It draws separate roles when a shared box would hide who controls a step, where data persists, or where a trust boundary lies. It puts approval and other conditions on the affected step. Optional paths can go in sourced notes. If a source leaves a material detail open, the guide calls for an explicit unknown. ## How to diagram a Run

Iris already has the entry points. The dev swarm map shows up to 20 Runs. It draws one edge per Run and destination pair and labels it with a count and summed latency. Run and destination nodes link to the Run page and filtered Run list. The Run page already reads journal rows in order and shows claims and call details. The demo Mermaid visualizer groups repeated attempts. A Run view can use that grouping and take claim verdicts from Verify. [Swarm map](../devpanel/map.py#L88) · [Map route](../devpanel/panel.py#L1940) · [Run detail](../devpanel/panel.py#L1118) · [Demo trace visualizer](../visualizer.py#L210)

1. **Start with the verdict and reason.** On the Run page, show the recorded Run state and the recorded verdict for the claim. Add a short next step from the read-back where available. On the swarm map, label the edge count as attempts. Keep its traffic outcome distinct from Verify. The current map color follows call outcomes and can be green on a Run with no call rows. [Map color](../devpanel/map.py#L58) · [Run summary](../devpanel/panel.py#L1118) · [Verify](../proxy.py#L1377)
2. **Give calls and control actions visible places in the sequence.** Use lanes for the Run, Iris, and recorded destinations. Show method, safe endpoint label, outcome, and any recorded status. A block at Iris ends there with the intended destination as a label. Mark CONNECT as one tunnel and show only its recorded metadata. Label a tool action only when there is a source for that action. The attempt table supplies proxy methods and outcomes. A call row alone supplies no tool name. Use journal order as recorded order. Show overlap only when recorded timing supports it. [Attempt fields](../db.py#L31) · [Row order](../devpanel/panel.py#L364) · [CONNECT block](../proxy.py#L1703) · [HTTP block](../proxy.py#L2214)
3. **Link the visible steps to local evidence.** Give each step a link to its journal row or the related rows in Run detail. Put recorded Verify and Steer actions on the Iris lane. For example, an allowed HTTP reply can be followed by a Verify call, an Incorrect result from a local read, and a Pause. Show those as distinct events. For an Unverified claim with reason No trace, show that reason and the next human step without drawing a call. In a long sequence, group routine attempts behind an exact count and keep blocks, verdicts, and pauses visible. The read-back method returns a detailed card and journals the call and verdict. A historical view can only show the detail that remains available. [Verify and Pause](../proxy.py#L1377) · [What counts as a trace](../db.py#L691)

## Where the analogy breaks

Archify lets the host agent choose an explanation and author the graph. Iris can use the layout ideas, but its events and verdicts must come from recorded evidence and deterministic checks. A repo citation can support what code is written to do. A proxy row can support what the proxy saw. A successful reply or tunnel byte count leaves a remote effect Unverified unless local proof establishes it. A diagram that passes every layout check still needs the same Verify and human retry gate. [Repository authoring](https://github.com/tt-a1i/archify/blob/main/archify/references/repository-authoring.md) · [Local read-back](../proxy.py#L1433) · [Verify requirements](../specs/verify-read-back-local/requirements.md)

Archify's shareable HTML can include source excerpts. Keep Iris evidence links local and use the approved metadata fields. Bodies, credentials, and raw private excerpts have no place in the picture. The existing server-rendered SVG and ordinary links can provide the drill-down within the dev panel. [Explainer sources](https://github.com/tt-a1i/archify/blob/main/archify/explainer/sources.mjs) · [Iris proxy contract](../AGENTS.md#proxy-contract) · [Iris SVG writer](../devpanel/map.py#L194)

## What I could not verify

The local clone could not connect to GitHub. I used the public README, skill, references, and implementation files served from `main`. The files were served from caches of different ages, so I could not pin the review to one commit. I also could not check how consistently the host agent chooses a faithful scope or how the delivered pages behave in Chrome. A clean checkout at one recorded commit would settle the source version. Running one prompt-based diagram and one repository-backed explainer through the host agent and inspecting the candidates, receipts, and rendered views would check the end-to-end behavior for those cases.
